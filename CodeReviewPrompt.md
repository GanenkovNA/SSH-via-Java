# Требования к Code Review (Java 21 + Maven)

> Обновлённая версия чек-листа.

---

## 1) Общие принципы
- **Единый стиль кода**: читаемость > краткость; имена по назначению, без неочевидных аббревиатур.
- **Явные контракты**: nullability, диапазоны, неизменяемость, потокобезопасность.
- **Fail fast**: ранняя проверка аргументов; осмысленные сообщения исключений.
- **DRY/SoC**: без дублирования, разделение ответственности; малые классы/методы.

---

## 2) JavaDoc — единые правила
- **Где обязателен**: public классы/интерфейсы/enum/record, публичные методы/конструкторы, базовые тестовые утилиты.
- **Структура**: (1) краткое «что делает», (2) контракты/инварианты, (3) шаги/нормализация (если важно), (4) примеры, (5) ссылки (RFC/man). Затем теги: `@param → @return → @throws → @implNote/Spec → @see`.
- **Nullability/исключения**: явно описывать условия `NPE`, `IAE`, `ISE` и т.д.; если параметр «может быть null», код не должен бросать NPE без оговорки.
- **Перегрузки**: одна «главная» с полным описанием; остальные — «Упрощённая версия {@link #...}» + отличия (например, дефолтные сообщения).
- **Enum**: описать смысл значений; единый шаблон `isValid`/`getIgnoreCase` ниже.

### Шаблоны
**Нормализатор (пример `normalizeForEnum`)**
- Шаги: trim → проверка пустоты → upper → `'-'` → `'_'`.
- `@throws`: `NPE` — если `input == null`; `IAE` — если пусто после trim().

**Setter в DTO (адрес/имя/MTU и т.п.)**
- Описать формат/диапазон, нормализацию, ссылку на валидатор; `@throws` с конкретными условиями.

**Enum API**
- `isValid(String)`: «возвращает `true/false`, **не бросает** исключений, нормализует как `getIgnoreCase`».
- `getIgnoreCase(String)`: «нормализует и возвращает значение; `NPE` при `null`, `IAE` при пустоте/неизвестном значении».

---

## 3) Архитектура и дизайн
- **Границы модулей**: явные зависимости; отсутствие циклов; «ядро» (DTO/валидаторы) не зависит от инфраструктуры (SSH/IO).
- **Валидация**: вынести повторяющиеся проверки (IP/MAC/MTU/имена) в отдельные валидаторы; DTO — только инварианты и простые предикаты.
- **Расширяемость**: enum-помощники и фабрики вместо «if/else каскадов»; предпочтение композиции.
- **Unknown-данные**: единый базовый тип для `unknownParams/unknownLines` (например, `BaseConfigDto`), чтобы избежать дублирования методов `addUnknownParam(...)`.

---

## 4) Качество кода
- **Исключения**: не конвертировать `IllegalArgumentException` в `RuntimeException` без причины; расширяйте сообщение и/или добавляйте cause.
- **Сообщения ошибок**: указывают *точный* параметр/значение (без путаницы между `address`/`broadcast`).
- **Иммутабельность где возможно**: `final` поля, неизменяемые коллекции в API; мутабельность — только внутри агрегатов.
- **Дублирование**: утилиты/шаблоны для однотипных сеттеров/валидаторов.
- **Малые методы**: одна ответственность; ранний `return` вместо вложенных `if`.

---

## 5) Производительность и память (без бенчей)
- Избегать лишних аллокаций в горячих путях (например, конкатенация строк → `StringBuilder`).
- Коллекции по назначению (`EnumSet`, `ArrayList` vs `LinkedList` и т.д.).
- Без преждевременной оптимизации: только явные точки нагрузки.

---

## 6) Многопоточность/ресурсы
- Явно документировать потокобезопасность типов; DTO по умолчанию **не потокобезопасны**.
- Владение ресурсами: кто создаёт/закрывает SSH-сессию; после `close()` повторное использование недопустимо — отражать в JavaDoc.
- Не блокировать надолго виртуальные потоки долгоживущими задачами; блокирующее I/O — ok для per-task виртуальных потоков.

---

## 7) Maven-специфика (без версий/порогов/CI)
- Стандартная команда сборки: `mvn clean verify -DskipTests=false`.
- Отчёты статических анализаторов публиковать как артефакты (локально/в CI), без жёстких гейтов.
- Профили/секреты — только через окружение; без хардкода в `pom.xml`.

---

## 8) Документация
- **README**: как собрать/запустить, ключевые сценарии, требования к окружению.
- **Примеры**: короткие фрагменты использования библиотечных API (сериализация DTO, SSH-сессия).
- **Ссылки**: RFC/man-страницы на сетевые форматы и состояния.

---

## 9) Специфика текущего проекта (точечные подсказки)
- В enum `isValid(...)` использовать `normalizeForEnum(input)` вместо варианта с пустыми сообщениями.
- Привести в соответствие JavaDoc↔код по nullability (например, `setGroup`: либо разрешить `null`, либо обновить JavaDoc).
- Исправить тексты ошибок, где подставляется неверная переменная (например, `setBroadcast`: использовать `broadcast`).
- Вынести `unknownParams/unknownLines` и повторяющиеся `addUnknownParam(...)` в общий базовый тип.


#  План обхода

## Порядок проверки (итерациями)

1. **Фундамент (helpers & validators)**
   - [x] `com.github.GanenkovNA.service.StringUtils`
   - [ ] `IpValidation`, `MacValidation` — требования к форматам, сообщения ошибок, граничные кейсы.
   -  Цель: выровнять API нормализации/валидации, чтобы дальше не спорить с DTO/enum.

2. **Enum-слой (контракты isValid/getIgnoreCase)**
   - [ ] Базовые состояния/типы:
      `dto.base.InterfaceState`, `dto.base.InterfaceFlag`*, `dto.base.QdiscType`*
      (\*если в репо)
   - [ ] IPv4: `dto.addr.v4.IpV4Scope`, `dto.addr.v4.IpV4AddressFlag`
   - [ ] IPv6: `dto.addr.v6.IpV6Scope`, `dto.addr.v6.GenerationFlags`, `dto.addr.v6.RouteFlags`
   -  Что проверяем: единый паттерн нормализации (через новую `normalizeForEnum(input)`), `isValid` не бросает исключения, `getIgnoreCase` бросает NPE/IAE по контракту, JavaDoc по шаблону.

3. **DTO-ядро (инварианты и ошибки)**
    - [ ] База/физика:
      `dto.base.InterfaceBaseConfigDto`, `dto.physical.InterfacePhysicalConfigDto`
   - [ ] Адреса:
      `dto.addr.v4.InterfaceIpv4ConfigDto`, `dto.addr.v6.InterfaceIpv6ConfigDto`, `dto.addr.LifeTimeParamsDto`
   - [ ] Агрегатор:
      `dto.InterfaceDto`
   - Что проверяем: диапазоны (MTU/префиксы), корректные сообщения (`broadcast` vs `address`), nullability ↔ JavaDoc, неизбыточность сеттеров, перенос дублированных `unknownParams/unknownLines` в общий базовый тип (если добавляем `BaseConfigDto`).

4. **Парсинг/команды (бизнес-логика преобразования)**
    - [ ] `IpA.showInterfaces(...)` и парсеры, которые он использует.
    - [ ] Что проверяем: разбор всех веток вывода `ip a`, покрытие edge-кейсов, отсутствие дублирующейся логики маппинга, корректная запись unknown\*, отсутствие скрытых зависимостей на формат локали.

5. **SSH/инфраструктура**
    - [ ] `SshSession`, `HostConfigReader`, `HostConnectionConfigDto` (или аналоги).
    - Что проверяем: владение ресурсами (кто закрывает), таймауты/реакция на сетевые сбои, чистые исключения (никаких «проглоченных»), явный контракт потокобезопасности.

6. **Сериализация/де-сериализация**
    - [ ] Jackson-аннотации в DTO, round-trip тесты (object → JSON → object), отсутствие лишних полей в JSON, `NON_EMPTY` на нужных местах.

7. **Тесты**
    - [ ] База: `TestBase` — закрытие сессии, зануление ссылок после `close()`.
    - [ ] Интеграционные: `ip.a.UnknownParamsTest`, `ip.a.OutputTest` — усилить проверками инвариантов (MTU, MAC, префиксы, наличие обязательных полей), негативные кейсы.
    - [ ] Добавить unit-тесты для валидаторов и enum (null/empty/case/dash).

8. **Документация**
    - [ ] JavaDoc по единым правилам (перегрузки без копипасты, чёткие `@throws`).
    - [ ] README: как собрать/запустить, краткие примеры использования (SSH-сессия, сериализация DTO).

---

## Формат каждой итерации

* Выбираем блок (например, «Enum-слой»), идём класс за классом.
* Для каждого: быстропроход по JavaDoc → API-контракт → типы исключений → мелкие правки (diff).
* Сразу добавляем/обновляем минимальные тесты на ключевые кейсы.
* Фиксируем изменения кратким changelog.
